# Fusion — 融合 kernel（Residual + RMSNorm → RoPE → SwiGLU）

> 目标：把两/三个 memory-bound 的算子合成一个 kernel，量化收益。
> 口径见 `bench/README.md`；可达带宽锚点 **763.5 GB/s**（`Operator/LayerNorm/bench_bw.cu` 的纯拷贝）。

## 为什么值得做

前几个算子（`Reduce` / `SoftMax` / `LayerNorm` / `RMSNorm`）最后都撞到同一句话：
**"单算子已经打满 DRAM，想再快只能减少搬运的字节数。"**

融合就是那个手段：把 `A 读一份写一份` + `B 读一份写一份` 变成 `读一次、写一次`。
注意它**不提高带宽利用率** —— 融合前后两版都会贴着 700+ GB/s，
收益 100% 来自"少搬了几个字节"。所以写代码之前必须先做一件事：**算字节账**。

## 题目：Residual + RMSNorm

```
hidden = x + residual                     # 残差流，下游的下一层还要用 → 必须落地
out    = rmsnorm(hidden) * gamma
```

输入 `x[M][D]`、`residual[M][D]`、`gamma[D]`；输出 `out[M][D]`，
并把 `residual` **就地**更新成 `hidden`（这就是 vLLM `fused_add_rms_norm` 的语义）。

未融合是两个 kernel：`add_kernel` + `rmsnorm_cached_kernel`（两个 `.cu` 里都写好当基线）。

## 字节账

数法：**逐趟 kernel 数"读了几个数组、写了几个数组"，一个 fp32 元素 = 4 B。**
`gamma` 只有 `D*4 = 16 KB`，所有 block 复用同一份、常驻 L2，不计入 DRAM。

| 方案 | 每元素读 | 每元素写 | 合计 |
| --- | --- | --- | ---: |
| 未融合 `add_kernel` | `x`, `residual` = 8 B | `hidden` = 4 B | 12 B |
| 未融合 `rmsnorm_cached_kernel` | `hidden` = 4 B | `out` = 4 B | 8 B |
| **未融合合计** | | | **20 B** |
| **融合** | `x`, `residual` = 8 B | `residual`(就地), `out` = 8 B | **16 B** |
| 陷阱：融合了、但第二遍从 global 重读 `hidden` | 12 B | 8 B | 20 B（**账面值 —— 实测不是这样，见下**） |

**理论上限 = 20 / 16 = 1.25x。** 别期待 3 倍：融合能省的字节占比，就是它的收益上限。

> **上面第三行是被实验推翻的那个结论，留在这里当例子。**
> 把第二遍改成重读 `residual[base+i]`（也就是自己刚写进去的 `hidden`）之后，
> ncu 量到的 DRAM 流量**仍然是 16.1 B/元素**，耗时也和寄存器版一样（2.94 ms vs 2.89 ms）。
> 原因：这次重读是**同一个 warp 在几十条指令前刚写过的同一行**，命中 L1，根本没走到 DRAM。
> SASS 里能数出来：这个 kernel 多了 **16 条 `LDG`**（= `ITEMS`，每个元素一条），而 `STG` 一条没多。
>
> **所以字节账真正的判据是"跨 kernel 的往返"**：未融合那两趟之间隔着 512 MB 的中间结果，
> 远大于 L2（48 MB），所以第二趟的读是实打实读 DRAM；而 kernel 内部对自己刚写过的数据的重读，
> 很可能一点都不花 DRAM 带宽。想确认有没有花字节上的钱，只有一个可靠办法：
> `ncu --metrics dram__bytes.sum`。
>
> 这也顺带换了种说法：**省下来的是"那趟 512 MB 的跨 kernel 往返"**，寄存器复用只是实现手段之一。

**自检信号**：如果算出来的有效带宽**超过 GDDR7 峰值 896 GB/s**，那一定是字节数算多了
（或者时间量错了）—— 物理上不可能。这个数比任何检查都灵。

## V0 结果（标量版）

口径：M=32768 / D=4096 / fp32 / Block=256 / ITEMS=16 / 同进程 A/B / median of 100。

| 实现 | ms | 有效带宽 | 账面字节 |
| --- | ---: | ---: | ---: |
| 未融合（`add` + `rmsnorm_cached`） | 3.5064 | 765.6 GB/s | 20 B/元素 |
| **融合 V0** | **2.8905** | 743.0 GB/s | 16 B/元素 |
| 加速比 | **1.213x** | — | 账面字节比 1.250x |

```
Check:
  [unfused out               ] max abs err = 4.77e-07 -> PASS
  [fused out                 ] max abs err = 4.77e-07 -> PASS
  [fused residual(in-place)  ] max abs err = 0        -> PASS
```

ncu 实测 DRAM 字节（`dram__bytes.sum`）：

```
add_kernel          12.4 B/元素
rmsnorm_cached       7.9 B/元素     -> 未融合合计 20.3 B/元素
fused_add_rmsnorm   16.0 B/元素     -> 字节比 1.27x
```

寄存器（`-Xptxas -v`）：`fused` 48 个、`rmsnorm_cached` 40 个、`add` 20 个，都没有 local memory。

**从 V0 学到的三件事**

1. 收益上限就是字节比（1.25x），实测 1.213x —— 这个"先算账再写代码"的模型是准的。
2. `fused` 的 DRAM 实测**正好 16.0 B/元素，一字节不多**，说明计数法用对了（跨 kernel 往返才落 DRAM）。
3. 融合**完全不提高带宽利用率**：未融合 765.6 GB/s、融合 743.0 GB/s，两版都贴着可达上限 763.5。
   赢在字节少，不是赢在跑得更有效率。

## V1：`float4` 向量化

融合已经打满带宽了，那 `float4` 还能赚什么？**注意它一个 DRAM 字节都不省** —— 还是 16 B/元素。
它能省的是另外两样东西：

1. **指令条数**：每个线程的 global 访问从 16 次 `LDG` + 16 次 `STG` 降到 **4 次 `LDG.128` + 4 次 `STG.128`**，
   地址计算和循环开销同步下降。
2. **`gamma` 的 L2 请求数**：`gamma` 每元素要读一次（4 B/元素 = 512 MB 的 L2→SM 流量，不落 DRAM），
   改成 `float4` 读可以把 L2 sector 请求数降到 1/4。

`V1.cu` 的 host 侧把**未融合 / V0 / V1 三个版本放同一个进程里计时**（跨 session 的绝对数字不能比，
同进程 A/B 才可以）。编译：

```powershell
cd Operator\Fusion
nvcc -O3 -arch=native -Xcompiler "/utf-8" V1.cu -o V1.exe
.\V1.exe
# 想扫 BLOCK（V1 支持 -DBLKV=512 之类）：一路 256 / 512 / 1024 各编一个
```

**要填的 TODO**：`fused_add_rmsnorm_v1_kernel` 里的下标映射与两个循环体。

**验收**：

- 四个 Check 全 PASS（未融合 / V0 / V1 的 out，以及 V1 的 residual in-place）；
- `V1` 的 ms ≤ `V0` 的 ms（只要不慢就算成功 —— 这一版的预期收益本来就是几个百分点）；
- `-Xptxas -v` 里没有 `local memory` / `spill`。

2. **`float4` 的真实收益只有 L2 那一项**：L2 read sector 35.49M → 34.07M（`gamma` 的请求压到 1/4），
   但 `gamma` 本来就不落 DRAM，所以时间上看不见。它什么时候才值钱？**当 L1/L2 侧真的卡住你时**
   （SIMT 循环里的地址计算、GEMM 里的 bank conflict）—— 那正是 `Operator/GEMM/` 里 V51 干的事。
3. **occupancy 高 ≠ 不是内存瓶颈。** 这条在 GEMM-TC 已经见过一次，这里是第二次：
   6 block/SM × 256 线程 = 1536 线程 = 满占用，照样在等内存。

## V2：`RMSNorm + RoPE`

```
y   = rmsnorm_per_head(x) * gamma_q     # 每个 head 单独归一化，head_dim = 128
out = rope(y, cos, sin)                 # 旋转位置编码：把每一对元素混起来
```

未融合就是两个 kernel：`rmsnorm_head_kernel` + `rope_kernel`（`V2.cu` 里写好当基线）。

### 字节账

| 方案 | 每元素读 | 每元素写 | 合计 |
| --- | --- | --- | ---: |
| 未融合 `rmsnorm_head_kernel` | `x` = 4 B | `y` = 4 B | 8 B |
| 未融合 `rope_kernel` | `y` = 4 B | `out` = 4 B | 8 B |
| **未融合合计** | | | **16 B** |
| **融合** | `x` = 4 B | `out` = 4 B | **8 B** |

**理论上限 = 16 / 8 = 2.00x** —— 比 V0 的 1.25x 高一档。

为什么上限变高了：融合省的字节数 = `2 × 中间张量的字节数`。中间张量在总访问里占的比例越大，
上限越高 —— V0 里 `hidden` 只占 4/20，这里 `y` 占了 8/16。
**所以挑融合对象比优化融合实现重要**：优先找"中间结果又大、下一趟还要完整读一遍"的算子对。

### 线程映射

```
一个 block = NWARP = 8 个 warp = 8 个 head = 1024 个元素
一个 warp  = 一个 head = 128 个元素 = 32 个 float4
一个 lane  = 一个 float4 = 4 个元素 = RoPE 的两对
grid.x     = M * NHEAD / NWARP = 131072
```

lane `l` 持有元素 `4l .. 4l+3` → RoPE 的两对是 `(4l, 4l+1)` 和 `(4l+2, 4l+3)`，
对应角度下标 `d = 2l, 2l+1`，正好是表里第 `l` 个 `float2`。

### 这一版的两个新东西

1. **归约维度变小。** 归一化不再针对整行 4096，而是每个 head 的 128 个元素 ——
   于是"一个 block 归约一整行"变成"**一个 warp 归约一个 head**"。
   坑：`__shfl_down` 归约完**只有 lane 0 拿到总和**，必须再 `__shfl_sync(..., 0)` 广播回 32 个 lane。
   好处：`__syncthreads` 和 shared memory **全部下岗**（`ptxas -v` 里 `0 barriers`、`0 smem`）。
2. **RoPE 是"混对"运算**：`(a, b) -> (a*c - b*s, a*s + b*c)`。
   融合之后 `y` 还在寄存器里，要配对的两个元素本来就在**同一个 lane** 手里 ——
   一次 shuffle、一次 shared 交换都不需要。这也是融合的隐藏红利：**不落地的中间量，连通信都省了。**

### 要填的 TODO

② warp 归约 + 广播出 `inv`；③ 归一化 → gamma → RoPE → 写回。

**验收**：两个 Check（未融合 / 融合）全 PASS；`speedup ≥ 1.7x`；

   全部消失，只剩 24 个寄存器和 `0 barriers`。**先看 reduction 的维度，再决定用什么同步原语** ——
   128 个元素根本用不到 block 这一层。

### 思考题（V2）

1. 如果 RoPE 换成 HF/NeoX 的 `rotate_half`（配对不是 `(4l, 4l+1)`，而是**前半块配后半块**，
   即元素 `i` 配 `i + HDIM/2`），当前这套"一个 lane 一个 float4"的映射还够用吗？不够的话最少要加什么？
   （提示：`i + HDIM/2` 在 float4 下标里差多少？）
2. 把 `NWARP` 改成 4 / 16 / 32 各量一次，`speedup` 会不会变？为什么？
   （提示：总字节数一字节没变。）
3. 每行 512 B 的 cos/sin 表被同一行的 4 个 block 各读一遍。如果 `HDIM` 翻倍到 256、
   或者 batch 远大于 cos/sin 的行数（多个 token 复用同一位置）时，这一项会不会开始值钱？
**一句话总结**：`Residual + RMSNorm` 只省得掉 4/20，所以上限 1.25x；`RMSNorm + RoPE` 省得掉 8/16，上限 2.00x。
**融合的上限只取决于"被消掉的那部分流量占总流量的比例"，和实现手段（寄存器 / shared / L2）无关。**

**思考题要点（V2）**

1. 不够用。`i` 与 `i + HDIM/2` 差 64 个元素 = **16 个 float4 下标**，所以要加一次
   `__shfl_xor_sync(0xffffffffu, v, 16)`（`__shfl_*` 不吃 `float4`，得按分量拆开）。
   换完之后每个 lane 手里同时有"自己那半"和"对面那半"，各算各的输出，不需要再广播。
   表大小不变（还是 `HDIM/2` 个角度），但每 lane 取的从 `float2 @ iv` 变成 `float4 @ (iv % 16)`。
2. 不会变 —— 已实测：`NWARP` 4 / 8 / 16 / 32 → 1.986 / 1.983 / 1.982 / 1.986x。
3. 现在就已经在花钱，只是很小：0.095 B/元素 ≈ 1.2%（见上面的对照实验）。
   而且这个比例 = **`1 / NHEAD`**，与 `HDIM` 无关 —— 表变大不会更贵，head 变少才更贵。
## V3：`SwiGLU`

```
out = silu(gate) * up          # silu(x) = x * sigmoid(x) = x / (1 + exp(-x))
```

### 字节账

| 方案 | 每元素读 | 每元素写 | 合计 |
| --- | --- | --- | ---: |
| 未融合 `silu_kernel` | `gate` = 4 B | `t` = 4 B | 8 B |
| 未融合 `mul_kernel` | `t`、`up` = 8 B | `out` = 4 B | 12 B |
| **未融合合计** | | | **20 B** |
| **融合** | `gate`、`up` = 8 B | `out` = 4 B | **12 B** |

**理论上限 = 20 / 12 = 1.67x** —— 又比 V2 的 2.00x 低。为什么？

因为 `gate` / `up` 都是"本来就存在、必须从 DRAM 读进来"的输入，融合只能省掉
"自己写出去又自己读回来"的那部分（`t`，8 B/元素），**省不掉 `up` 的 4 B**。

于是得到融合的通用公式：

```
收益上限 = 1 + (被消掉的中间量字节) / (融合后的总字节)

V0: 1 + 4/16 = 1.25x      V2: 1 + 8/8 = 2.00x      V3: 1 + 8/12 = 1.67x
```

**推论**：一条"读 2 写 1"的 elementwise 链，不管怎么融合，上限都不会超过 **2x** ——
因为下游总得再读进一个新输入。想突破 2x，只能去干掉那个"新输入"本身，
也就是**把它融进上游 GEMM 的 epilogue**（那是后面接 GEMM-TC 的活）。

### 这一版的新东西：把计算塞进搬运 kernel

前两版的 kernel 基本只做地址计算和乘加，这一版第一次往里塞了**超越函数**。
判断"能不能白塞"的尺子是本机的算力预算：

```
FP32 峰值 ≈ 44.75 TFLOPS      可达带宽 ≈ 763.5 GB/s
-> 每搬 1 字节，可以配 ~58 条 FLOP
```

文件里 4 个 kernel：

| kernel | 作用 | 字节 |
| --- | --- | ---: |
| `silu_kernel` | 未融合 1/2：读 `gate` 写 `t` | 8 B/元素 |
| `mul_kernel` | 未融合 2/2：读 `t`、`up` 写 `out` | 12 B/元素 |
| `copy2_kernel` | **对照组**：读两个数组直接相加写回，不算激活 | 12 B/元素 |
| `fused_swiglu_kernel` | 融合版（TODO） | 12 B/元素 |

对照组和融合版**字节数一模一样**，两者时间之差就是"算 silu 的价格"。

**从 V3 学到的三件事**

1. **上限公式是 `1 + 省掉的中间量 / 新总字节`。** V0 1.25x、V2 2.00x、V3 1.67x 全都对得上，
   而 V3 还给出推论：elementwise 链（读 2 写 1）的融合上限封顶 2x。
2. **激活在这个 kernel 里真的是白送的**：指令数差 10 倍、寄存器差 9 个，时间差 0.4%。
   SM 侧的发射槽只用了 **3~7%**，DRAM 用掉 **89%** —— 纯内存瓶颈，算力预算还剩 90%。
   所以 memory-bound kernel 里"顺手算点东西"几乎不要钱（前提是别把它们做成依赖链瓶颈）。
3. **贵的是除法，不是 `exp`。** `x / y` 在默认编译下是完整 IEEE 除法（`MUFU.RCP` + 两轮牛顿迭代 + 边界处理），
   一个元素 ~19 条指令；换成 `__fdividef` 直接从 488 掉到 184。**但在 DRAM roofline 上，
   这 300 条指令的差别只值 0.4%。** —— 先确认瓶颈在哪，再决定要不要优化指令数。

### 思考题（V3）

1. 为什么 V3 的上限（1.67x）比 V2（2.00x）低？用"到底省掉了哪部分流量"回答，
   并说出这个公式在什么情况下能超过 2x。
2. 对照组 `copy2` 和融合版字节数一样，时间差多少？把 silu 的价格和"每字节 ~58 FLOP"的预算对一下。
3. `__expf` → `expf`、`x/y` → `__fdividef(x,y)`：指令数各变多少？时间变吗？为什么？
4. 如果 `up` 是上游 GEMM 刚算出来、根本没落过 DRAM 的，V3 的上限会变成多少？
   这时候"融合"该往哪边做？
**思考题要点（V3）**

1. 分子其实**一样**（V0/V2/V3 都省 8 B：中间张量的"写 4 + 读 4"），差的是**分母** ——
   V2 融合后只剩 8 B/元素，V3 还剩 12 B/元素（`up` 是真输入，省不掉）→ 2.00x vs 1.67x。
3. 贵的是**除法**不是 `exp`：默认的 `x / y` 是完整 IEEE 除法（`MUFU.RCP` + 两轮牛顿 + 边界处理），
   一个元素约 19 条指令；换 `__fdividef` 让指令数从 488 掉到 184 —— 但时间只差 0.4%。
4. **`3.0x`，不是 `2.0x`。** 若 `up` 来自上游 GEMM 的累加器、从不落 DRAM，
   消灭它同时干掉**两份**字节（GEMM 写 `up` 4 + `mul` 读 `up` 4 = 8 B）：
   完整链路 `GEMM 写 up 4 + silu 8 + mul 12 = 24 B/元素` → 融进 epilogue 后只剩
   `读 gate 4 + 写 out 4 = 8 B/元素` → **24 / 8 = 3.0x**
   （通用公式验算：`1 + (t 的 8 + up 的 8) / 8 = 3.0`）。
   所以"读 2 写 1 封顶 2x"只适用于**两个输入都真在 DRAM 里**的 elementwise 链。
## 总结：融合这条线

### 一张总表

| 版本 | 链条 | 字节/元素（未融合 → 融合） | 理论上限 | 实测 | 这一版学到的新东西 |
| --- | --- | --- | ---: | ---: | --- |
| V0 | `x + r` → `rmsnorm` | 20 → 16 | 1.25x | **1.213x** | 先算字节账；中间量留在寄存器里 |
| V1 | V0 的 `float4` 版 | 20 → 16 | — | 1.002x（vs V0） | 指令数不是瓶颈，字节数才是 |
| V2 | `rmsnorm_per_head` → `rope` | 16 → 8 | 2.00x | **1.983x** | 归约维度决定同步原语；混对运算可以免通信 |
| V3 | `silu` → `mul` | 20 → 12 | 1.67x | **1.683x** | 往搬运 kernel 里塞计算，几乎免费 |

四条链的实测全部顶到理论值的 **95% 以上**（V3 甚至略超，因为未融合那侧带宽没跑满）。

### 1. 收益上限：一个公式管到底

```
收益上限 = 1 + (净省掉的字节) / (融合后的总字节)

V0: 1 + 4/16 = 1.25x    中间量 hidden 的"读"省掉了，但"写"必须保留（residual 要就地更新）
V2: 1 + 8/8  = 2.00x    中间量 y 的"写 4 + 读 4"两份全省
V3: 1 + 8/12 = 1.67x    中间量 t 的"写 4 + 读 4"两份全省
```

注意分子是**净省掉的字节**，不是"中间张量的大小"：
一个 fp32 元素往返一趟是 `写 4 + 读 4 = 8 B`，但如果融合之后仍然得写出等价的一份
（V0 的 residual 就地更新），就只能算其中一份 —— **这就是 V0 只有 1.25x 的根本原因**。
而分母是"融合之后**还得搬**的那些字节"，分母越大收益越小（V3 有一个必须保留的真输入 `up`）。

### 2. 融合不提高带宽利用率，一字节都不提高

| 版本 | 未融合 | 融合 |
| --- | ---: | ---: |
| V0 | 765.6 GB/s | 743.0 GB/s |
| V2 | 755.1 GB/s | 748.8 GB/s |
| V3 | 774.0 GB/s | 781.7 GB/s |

两版都贴着可达上限 **763.5 GB/s**。**收益 100% 来自字节数减少**，不是跑得更有效率。
推论：动手之前先算字节账；算出来省的比例很小，就直接别做。

### 3. 上限之外顺手能拿的（都不值钱）

- `float4` 化：指令数 ÷4、L2 请求 ÷4、寄存器 −8、占用率 78% → 95% …… 换来 **+0.2%**
- 归约维度从 4096 缩到 128：block 归约 → warp 归约，shared memory 和 `__syncthreads` 全部下岗
  （V2 的 `0 barriers / 0 smem`）
- 往 memory-bound kernel 里塞一整个 silu：指令数差 **10 倍**，时间差 **0.4%**
  （发射槽只用了 5.9%，DRAM 用掉 88.8%）

**共同点：只要 kernel 贴着 DRAM roofline，SM 侧的一切优化都换不来时间。**
这三条在 `GEMM-TC` 里已经见过一次（六版 occupancy 都 29~31%，照样提速），Fusion 是更干净的重演。

### 4. 想突破 2x，只能往外走

有一条硬约束：**"读 2 写 1"的 elementwise 链，融合上限封顶 2x** —— 下游总得再读进一个新输入。
突破的唯一办法是让某个输入不再从 DRAM 来：**把融合往上游搬，融进生产者（GEMM）的 epilogue**。
V3 第 4 题给了量化版：`up` 一旦是 GEMM 累加器里现成的、从不落地，
同样的融合从 1.67x 变成 **3.0x**（因为同时干掉了"GEMM 写 up"和"mul 读 up"两份字节）。

### 5. 融合的代价（别只算收益）

- **通用性下降**：V1 那版要求 `D % (4*BLOCK) == 0` 且 16 B 对齐，不满足直接 `misaligned address`；
  标量版没这个限制，但它会静默丢尾部。
- **并行度自由度下降**：融合后必须同时满足两个算子的切分需求（epilogue 融合要迁就 GEMM 的 tile）。
- **不能复用现成的高性能库**：融合版只能手写，出 bug 要自己扛。
- **寄存器压力上升**：V2 的融合把 `y` 一直留在寄存器里 —— 数据量再大一点就得溢出到 local memory。

所以工业界的做法是**只挑收益最大的那一两处融**（残差 + RMSNorm、RoPE、SwiGLU 的 epilogue），
而不是见到相邻算子就融。
## 工程注意（踩过的坑）

- **中文字符串别贴着结尾的引号。** nvcc 的**设备前端**按本机代码页（GBK）解析 `.cu`，
  `-Xcompiler "/utf-8"` 只管 host 编译器。UTF-8 汉字的尾巴（如 `倍` = `E5 80 8D`）里最后一个字节
  `8D` 在 GBK 里是合法首字节，会把后面的 `"` 当成第二个字节吃掉，报 `error: missing closing quote`。
  对策：字符串字面量写 ASCII；非要写中文，就在汉字后补一个 ASCII 字符。
  **注释里的中文不受影响** —— 同一个目录里 `V0.cu` 编得过、`V1.cu` 编不过，就是这个原因。
- **ncu 的 duration / 字节数跨进程会漂。** 同一条命令跑两次，V1 先得到 3.85 ms / 16.87 B/元素，
  再跑一次是 2.81 ms / 16.09 B/元素。**只信同一次 run 内的相对值。**
- **向量化有两个前提，不满足是直接挂，不是变慢。**
  ① **对齐**：`reinterpret_cast<float4*>` 要求行首 16 B 对齐 —— 行的起始元素是 `row*D`，
  字节地址 `row*D*4`；`D % 4 != 0` 时它 `% 16 != 0`，运行时直接 `misaligned address` 报错。
  ② **整除性**：本文件还要求 `D % (4*BLOCK) == 0`（`VITEMS` 得是编译期常量、一个 block 要恰好铺满一行）。
  顶上那两条 `static_assert` 钉的就是它 —— 只满足 `D % 4 == 0` 还不够。
  标量版没有对齐要求，但它**不通用**：`ITEMS = D/BLOCK` 向下取整，`D` 不被 `BLOCK` 整除时尾部元素被**静默丢掉**（不报错，结果是错的）。
- ncu 默认锁 base 时钟，duration 比 standalone 高（这里 +14% 左右），绝对值别拿去和 standalone 比。
